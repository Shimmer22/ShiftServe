# 固定 H 的 CPU/HTP 分阶段扫描

配置在 `configs/pd-stage-sweep-h4096.json`。本次固定 Qwen3.5-9B-Q4_0、H=4096、8192 context、batch128、4线程、F16状态，CPU和HTP显式加载；无KV整理、预搬移和OpenCL。服务的 route 名称只表示加载两个后端，本实验不执行成本模型选路。

P 为 16、24、26、28、30、32、34、36、38、40、48、64、80、96、112、128、192、256。D 为 1、8、16、32、48、64、96、128、192、256、320，decode 固定 P=40。

真实 BFCL 轨迹提供 token 内容：取同一 prompt 的前4096个token作为固定历史，随后取各长度的输入；强制输出取同一原始响应的前320个token。因此它是长度受控的阶段微基准，不是原任务原样重放，不评价工具调用或回答质量。

完整 H 通过 FrozenReplayCache 首次建立，后续所有点使用同一内存快照，并保留私有磁盘快照。恢复包含完整 KV/recurrent/conv 状态字节检查，不能通过简单裁剪状态伪造。模型初始化、历史建立、恢复和有限值检查不进入纯阶段时间，分别保留记录。

每轮随机化18个P点和1次完整decode的顺序，轮换两个后端的先后，共三轮、57个双后端请求。P点不执行decode。D每后端连续逐token调用至320，在11个检查点记录累计时间，避免重复计算输出前缀。检查点的有限值检查和记录开销从累计时间中排除。所有调用同步，decode时间包含逐token调用与同步开销，不包含采样。

先验证正常文本响应，再通过短历史功能检查，执行 H=4096/P=40/D=8 的预热。检查完整状态恢复、形状和有限logits，单独报告CPU/HTP prefill logits余弦相似度是否≥0.99。原始响应先落盘，机制或协议失败保留 `.raw.json`，不作为通过结果进入汇总。数值一致性不通过时保留显式标记，不据此筛掉性能点。性能不能替代自由生成质量验证。

首次 H32/P8 功能检查的完整状态恢复与有限值检查通过，但余弦相似度0.98879低于0.99，原采集器停止。该输出和停止状态保留在 `diagnostics/`。随后明确分离机制准入与数值一致性标记，补正常响应检查再恢复采集；不更改原测量值或数值阈值。

入口：

```sh
python scripts/collect/pd_stage_sweep.py \
  --binary results/20261111-pd-stage-sweep-h4096/build/agent
```

后台通过独立进程会话启动；Mac 运行 caffeinate 保持清醒，聊天可以关闭，Mac及手机仍需保持联网。仅通过Termux SSH管理手机并持模型锁。断线时等待同一服务计算结束，核对健康身份后串行重试；计算或协议失败立即停止并保留日志、服务和锁。相同构建和配置可以重跑同一入口，校验并跳过已有完整结果；不存在通用崩溃后自动恢复保证。

结果在 `results/20261111-pd-stage-sweep-h4096/`：`status.json` 为进度，`background.log` 为后台日志，`measurements/` 为原始测量，`stage-times.csv` 为174行阶段数据（108个prefill点、66个decode检查点）。完成后只停止本次服务，收回日志并释放模型锁；手机快照保留。

## 密集区独立复测

`configs/pd-prefill-dense-h4096.json` 只扫描 P=26、28、30、32、34、36、38，三轮，共21个双后端请求、42条prefill耗时，不重测D。复用相同服务二进制与上一轮的私有完整历史缓存；缓存仍逐次检查模型/构建/上下文/精确token和状态字节，不重建4096-token历史。

结果单独保存到 `results/20261111-pd-prefill-dense-h4096/`。按用户要求，`scripts/plot/pd_prefill_dense.py` 对所有有效耗时统一画图和计算均值，不区分数值一致性标记；原始数值检查仍保留在JSON和CSV中，不删除日志。独立大图为 `figures/prefill-dense.png`，同时导出PDF/SVG。

## CPU 六线程、每点十次

`configs/pd-prefill-dense-h4096-cpu6-t10.json` 沿用上述7个P点，CPU的 `n_threads` 和 `n_threads_batch` 均为6，HTP上下文的主机线程保持4。每个后端每个P正式测10次，共70个双后端请求、140条耗时。十轮随机P顺序并轮换CPU/HTP先后，功能检查与预热另记，不混入正式重复。

线程数通过 `A2O_CPU_THREADS` 显式传入私有服务，健康信息、服务清单、逐响应和CSV均记录实际配置并校验。新构建及CPU线程进入缓存身份；不把旧四线程的状态当成新配置缓存，首次建立H4096后再复用本轮内存/磁盘快照，不改写旧结果。

单独结果目录为 `results/20261111-pd-prefill-dense-h4096-cpu6-t10/`。独立后台会话运行，完成后保存CSV、停止本次服务并释放锁；依用户要求，等用户提示后再验收、作图，不自动发布新图。

延伸至P40：`configs/pd-prefill-dense-p26-40-h4096-cpu6-t10.json` 对26、28、30、32、34、36、38、40完整重测十轮，共80个双后端请求、160条耗时。复用六线程版同一二进制与完整历史快照，不混入旧四线程构建。结果单独保存在 `results/20261111-pd-prefill-dense-p26-40-h4096-cpu6-t10/`，绘图入口仍为 `scripts/plot/pd_prefill_dense.py --input <本轮结果>/stage-times.csv`。

逐整数扩展：`configs/prefill-p24-64-128-cpu6-t10.json` 扫描24至64的全部整数，再翻倍至128，共42点。每点每后端10次，共420个双后端请求、840条耗时；每轮P按固定种子乱序，每个P恰有5次CPU先测、5次HTP先测。H4096、CPU6线程、HTP主机4线程及其他配置保持一致，复用相同构建的六线程历史缓存。独立结果目录为 `results/20261111-prefill-p24-64-128-cpu6-t10/`。

用户澄清“翻倍”为相对64的偏移量2、4、8、16、32、64，即64后取66、68、72、80、96、128。原扫描继续，`scripts/collect/pd_geometric_extension.py` 等原扫描完成并释放锁，再按 `configs/prefill-geometric-supplement-cpu6-t10.json` 串行补测66、68、72、80、96，每点每后端10次、P乱序、后端先测各5次。最终47个P点、470个双后端请求、940条耗时，合并目录为 `results/20261111-prefill-p24-128-geometric-cpu6-t10/`。合并核对构建、token源、H、上下文、线程与重复轮次，逐行保留source_run；新增五点为原扫描之后的追加批次，不宣称两批次在同一时段交错执行。
