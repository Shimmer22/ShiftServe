# Agent 缓存失效来源与机制候选

现有证据支持研究“保持可复用上下文，并在可恢复状态边界提交”的机制候选。当前约 6.76 倍的结果只针对 18 个新增函数边界的主机 prefill，包含工具说明布局改变和历史空 think 标记稳定两项操作，还受到本次混合模型状态检查点策略影响。它不是已经验证的通用 Agent 加速，也不是 Tool Gap E2E。

## 先区分三种量

相对于本次选择的上一冻结序列，记当前输入长度为 N，精确 token 公共前缀为 H，服务指标报告的实际缓存命中为 C。本次协议每条件清空缓存、只预热上一冻结序列，因此 C≤H。

- N−H：位于首次 token 分叉之后的输入，旧状态不能直接复用。其中既有真正新信息，也可能有被重写牵连的旧历史。
- H−C：输入本可匹配，但运行时没有恢复对应状态的部分。检查点、缓存策略和兼容性都可能造成该缺口。
- N−C：本次未从前缀缓存提供的输入 token；不是精确 FLOP 或耗时模型。

一般服务可能命中比上一请求更早保存的其他序列，故不能把“相对上一次请求的 H”无条件当作全局缓存命中上限。诊断必须同时记录实际选择的缓存来源。

## 已有 Agent 的已观测来源

| 原因 | 证据 | 意义 |
|---|---|---|
| 前部工具目录插入 | BFCL 18 次新增函数公开均在旧 prompt 内部分叉 | 插入点后的旧历史即使文本相同，也不能直接使用旧上下文状态 |
| 历史重新序列化 | 204 次其他跨用户轮全部破坏旧 prompt 文本前缀；双方移除空 think 标记后，204/204 恢复旧 prompt 文本前缀 | 在本批关闭 thinking 的轨迹上，这是模板行为而非用户新增信息导致的变化 |
| 可恢复检查点不足 | 四布局 72 次实际缓存命中全部符合本次 528-token 最后对齐检查点规则 | 逻辑 H 增长不保证物理命中增长，跨过状态检查点后可出现跃升 |
| 手机 live 锚点较保守 | ToolSandbox 首轮 CPU 217 次后续推理中，168 次实际评估 P 大于逻辑 P；中位数 77 vs 49 | 锚点在 prompt 完成时，decode 工具调用需要重新评估；这是明确的设计限制，不等同缓存被逐出 |

普通 513 个后工具边界中，旧 prompt 文本全部保持为新 prompt 前缀；512 个还完整保留原 prompt+生成 token 序列，另一个在生成尾部存在 token 差异。因此不能把正常工具返回普遍描述成长历史失效。

移除空 think 后的检查针对 prompt 文本，不证明完整 prompt+generated IDs 都可复用。当前实验只处理关闭 thinking 时的空标记；不能扩展成“永远保留所有历史推理文本”的规则。

手机额外评估量共 5101 token：逻辑 P 总计 14945，实际评估总计 20046。本批没有发现逻辑 H>0 却 H_anchor=0 的整段重置。此处是单独数据集、单独 CPU 服务，不与主机 18 边界的缓存命中混算。

尚未证实的其他来源包括：检索文档或示例重排、历史摘要/裁剪、时间戳与会话标识进入头部、消息 ID/参数序列化不稳定、状态被逐出、模型或模板版本变化、设备状态不兼容。这些是后续审计项，不当作现有数据结论。

## 本次漂亮结果到底做了什么

1. `rules_first`：把系统段的固定调用规则与说明移到可变工具目录前。保留当前全部可用工具定义与公开时点。这只多保护一段固定内容。
2. `append_docs`：工具目录固定为任务最初版本，新增函数定义只保留在原来公开轮次的用户更新消息中。原适配器在头部 tools 与更新消息中都放入新增定义；本条件去掉了头部插入。它把工具说明从系统目录层移到了已有用户更新层，不能仅凭字面内容保留就断言语义等价。
3. `append_docs_stable_history`：在第 2 条基础上，为缺失空 think 块的历史 assistant 恢复该标记，使旧序列不因跨用户轮模板重绘而改变。

| 布局 | H 总量 | 实际 C 总量 | N−H | H−C | N−C | prefill 总计 |
|---|---:|---:|---:|---:|---:|---:|
| native | 59179 | 0 | 27207 | 59179 | 86386 | 9.950 s |
| rules_first | 62671 | 7392 | 23715 | 55279 | 78994 | 9.180 s |
| append_docs | 71533 | 29040 | 12255 | 42493 | 54748 | 6.595 s |
| append_docs_stable_history | 79582 | 74976 | 4622 | 4606 | 9228 | 1.473 s |

不同布局 N 不完全相同：新增定义去重减少输入，历史空标记保留增加输入；以上是实际长度而非强行固定相同 token 数。N−H 下降既包含避免旧尾部重算，也包含移除重复定义，不应都归因于“缓存算法”。

四条件没有“仅稳定历史、保持动态目录”这一项，尚不是完整 2×2 因子消融。现有增量结果可证明在工具更新不再破坏头部的条件下，稳定历史进一步提高复用；不能精确分配两个操作的独立贡献或交互贡献。

## 528-token 检查点现象

捕获的服务日志明确记录，为匹配 Mamba 状态页，attention block 被设为 528 token。已安装 vLLM 的 MambaManager 在 align 模式下维护最后状态块，内部位置的状态与普通 attention KV 不同。

令上一预热输入长度为 L，在本批 72 次测量中：

```text
q = floor(L / 528) * 528
C = q，若 H ≥ q
C = 0，若 H < q
```

该经验规则与实际计数 72/72 一致。它只适用于这次引擎配置及单次上一序列预热协议，不推断所有 vLLM 配置、所有检查点策略或手机后端都如此。

选中的 `miss_func_194/t05-s00`：原版 H=2750，而上一序列的最后对齐检查点为 4752，实际 C=0；追加说明后 H=4952，能够使用 C=4752；再稳定历史后 H=5241，但 C 仍为 4752，因此该例逻辑 P 431→186 并没有进一步增加实际命中。prefill 两者都约 0.107 秒。

这是值得机制化的运行时约束：输入保持与状态检查点必须配合。也存在更强的简单基线——在原布局下保存更多合法检查点。尚未做该反事实实验，不能把现有 6.76 倍推广为相对最强缓存实现的收益。

## 可泛化机制候选

候选目标：在保持消息角色、工具权限、生效时点和任务语义的约束下，尽量将上下文更新表示为追加事件；对不可避免的历史修改，显式定位失效边界，并保存/选择相应完整状态检查点。

可以由四个具体部分组成：

1. 记录消息段及其来源、角色、版本和 token 边界，诊断首次分叉是新增信息还是重新序列化。相同字符串并不代表跨历史状态可直接拼接。
2. 稳定构造已经提交的历史 token；工具目录更新、检索结果和用户消息只在语义允许时以增量追加。真正需要修订、撤销或裁剪的内容按新版本失效，不能强求 append-only。
3. 对照后端的真实状态能力选择检查点，保证 KV、recurrent、conv 和位置一致。在 Tool Gap 内可考虑准备这些状态或稳定前缀，记录准备成本、缓存空间、未命中回退与版本匹配。
4. 返回后先核对权威版本与精确 token 前缀，再使用可恢复检查点，并用实际残余输入重做 CPU/HTP 成本选路。不能直接沿用旧 P=32 或旧成本模型。

研究贡献不能只建立在去掉特定模板的空标记上。它需要在多种失效来源与 Agent 实现上优于“修好模板＋普通前缀缓存”，并证明检查点预算和准备调度的额外价值。

## 首要验证顺序

1. 补齐 2×2 因子条件：原版、仅稳定历史、仅增量工具说明、两者结合；固定规则前移继续作为简单对照。重复测量并报告相同条件下的输出与质量。
2. 加入“原布局＋更充分检查点”以及“修好模板＋普通缓存”强基线，拆开文本布局和引擎状态限制的贡献。
3. 对全部 60 题完整回合重跑官方评分，按基础情节划分，覆盖正常多轮、缺参数与缺函数。单边界 16/18 一致和原通过任务 8 个边界一致均不能替代完整质量。
4. 扩展到确实发生检索、记忆或工具更新的自然轨迹；记录 N/H/C、检查点位置、首次分叉段及准备开销。无失效场景是必要负对照。
5. 最后再回到手机 CPU/HTP，测真实 Gap 下的完整状态准备、返回后选路与端到端收益。当前 18 个案例属于新用户轮开放函数，不是工具结果到达边界；不能直接当作 Tool Gap 机制的端到端证据。

风险最大的假设是：在修复模板并提供合理检查点后，真实 Agent 仍有足够频繁、足够昂贵、且能在语义不变条件下推迟的上下文修改。如果这一假设不成立，应保留修复而缩小机制范围。
