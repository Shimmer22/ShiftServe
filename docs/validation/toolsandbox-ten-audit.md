# 十题三条件审计：精度、失败与人工干预

## 已确认的结论边界

此前“没有KV压缩/裁剪”和“完整sequence状态字节一致”只能证明对应机制没有主动丢弃状态，不证明CPU/HTP计算数值相同。旧校准只检查prefill logits cosine≥0.99及D=4 greedy IDs，不能保证完整回答或任务评分不变。此前按共同完整九题给出的10.7%/0.13%耗时差不能作为同等质量加速结论。

证据目录为 `results/20261107-toolsandbox-route-e2e/`；原始正式binary为 `build-service-143119/agent`，不能用之后修改的当前源码代替其源manifest。

## 轨迹为什么失败、评分为什么不同

1. **真实同输入生成分歧。** 独立校准H545/P137三次cosine均约0.996429，但CPU首token为40、HC为248058，分别导向自然语言确认与工具调用。完整状态可迁移不等于低精度HTP内核与CPU运算等价。
2. **完整生成检查不足。** 四token一致并不覆盖之后所有decode、grammar和反复跨后端的误差累积。正式最近消息任务step001相同prompt下CPU/HTP首token不同；CPU/route第12token出现措辞差异。尚不能全部归因为后端固有误差，需要固定输入回放隔离状态迁移、logits传递及采样实现。
3. **工具输入不配对。** 官方工具调用实时时钟和uuid4，CPU/HTP/route顺序运行时返回值不同。发信、提醒创建返回不同UUID；日期、提醒查询返回不同timestamp，后续prompt因此不同。固定模型seed不会固定这些值。
4. **提醒任务循环。** CPU使用5次生成/4次工具结束；HTP和route各15次生成并反复调用timestamp_to_datetime_info，触及官方30步上限。最后工具结果没有被下一请求消费，采集器标记unconsumed tool result events。它是未完成轨迹，不应删除、重命名成成功或仅提高步数隐藏。
5. **评分不是二元正确率。** 官方similarity包含工具、状态和语言里程碑；自然语言改变可影响总分，工具动作改变也可影响实质成功。必须逐里程碑分析，满分率、平均相似度和轨迹完整率分开报告。

CPU正式10/10完整，HTP与route各9/10；平均官方分数分别0.7413、0.8531、0.7116。由此不能声称本轮不损伤精度。HTP路径是CPU KV及不支持算子的CPU执行加HTP权重offload，不是全算子纯NPU。

## 为什么发生多次人工干预

| 原因 | 实际影响 | 需要的修复 |
|---|---|---|
| 一次性脚本硬编码目录、非幂等mkdir | resume撞已有目录，再次退出 | 唯一attempt目录、持久状态、按完成记录续跑 |
| SSH启动返回255，未核对是否真的启动 | 无法判断服务在跑还是未启动 | 核对owner/PID cmdline/health，幂等reconcile后再决定 |
| wake-lock偶发超时，无重试策略 | 服务启动前退出 | 有界重试并复核双时钟，保留失败attempt |
| 将单题轨迹失败视为全批异常 | HTP第9题失败导致route未启动 | 题目失败落盘后继续；基础设施故障另分类恢复 |
| 异常后服务和锁保留但没有恢复执行者 | 模型空闲占锁，用户以为仍在采集 | 异常恢复/清理、heartbeat和状态时间戳 |
| 本地runner虽后来detach但缺少checkpoint和监护 | 断线后需要人工判断和续接 | detached持久状态机，逐题原子checkpoint，启动自动恢复 |
| 状态通报只检查启动时而未核对最新推进 | 用户获得过时的“正在运行”印象 | 同时核验进程、最新文件、当前题、心跳及错误状态 |
| 9B服务/策略尚未接通就开始整批组织 | 现场发现HTP KV映射和协议差异 | 先短回归通过，再冻结源码hash与配置启动正式轮 |

前四项属于实现与执行流程不足，不应由用户反复询问来发现。不能把网络偶发故障或模型失败作为需要用户手动续跑的常态。

## Full的验收要求

用户已确认范围：single_tool_call 19题＋multiple_tool_call 54题，共73道基础题，CPU/HTP/route三条件。不含多用户轮、干扰工具augmentation或insufficient-information题集。

先建立受控时钟/UUID/初始数据库的配对输入和固定输入数值回放；保留官方评分器，明确受控环境改动。完整状态与完整生成分别验收，禁止将4token校准称作全程无损。若严格token无损无法实现，真实报告质量边界；不得用隐藏CPU重算、强制CPU答案或选择成功子集来制造无损与加速。

运行器必须通过启动应答丢失、旧目录、SSH断连、题目步数上限、重启续跑等故障检查，才允许启动Full。每题失败仍保留，剩余题和条件继续；基础设施故障通过幂等有界恢复；失败attempt不覆盖。只有完整尝试73×3并生成报告、释放服务与锁，才标记实验完成。
