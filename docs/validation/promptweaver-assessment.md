# 对照 Agent-X §4.2、Figure 11/12：当前是否存在同量级机会

结论：`fuelLevel` 不适合作为主要加速方向。前一份报告把它作为格式例子合理，但将它列为优先 prefill 候选偏乐观。我们与 PromptWeaver 最接近的对象是较长的工具说明与其插入位置，不是观测 JSON 的字段名。当前后工具短 P 场景尚没有同量级的长静态片段证据。

## 论文具体缓存什么

Figure 11 将长说明和示例组织为稳定前缀。Figure 12 用工具共激活关系组织示例，并为固定顺序下的若干前缀组合缓存状态。它不是为每个工具响应建一个独立 KV 然后任意拼接；组合之前的上下文也必须一致。本文原图已逐张查看，来源为 [Agent-X §4.2](https://arxiv.org/html/2605.10380v1)。

## fuelLevel 的实际规模

已有 BFCL 中仅含 fuelLevel 一个字段的返回共有 22 条，正文为 9–10 token 左右，P 为 26 或 27。对实际 prompt token 求共同前缀，得到 11 token，其中 6 token 是通用工具消息开头，fuelLevel 字段自身仅再贡献 5 token。

而且 11 token 是在“实际返回成功且只有 fuelLevel 字段”的条件下得到的。`fillFuelTank` 也会返回容量错误；事先不能把成功字段前缀当成一定出现。

这是一小段可匹配前缀，不等于一个长输入块的离线缓存。对这 5 个字段 token 另开准备/计算阶段，可能因小 batch、完整状态管理、验证与选路成本而没有净收益，尚未做消融。不能用 token 比例直接换算毫秒。

当前保存的一个 P=27 CPU 边界 prefill 约 3.87 秒、decode 约 15.41 秒、合计约 19.28 秒；该边界是其他工具，不能称为 fuelLevel 实测，但说明即使整个短 P 的 prefill 被消除，decode 仍不变。字段前缀只覆盖其中一小段。BFCL 的实际沙箱 G 中位数约 0.193 毫秒，更不能假设能隐藏秒级准备。

## 扩大到所有请求后，真正的长块在哪里

此前 513 边界统计仅覆盖工具返回。现在补查全部 795 次已有推理请求：

| 请求类别 | 次数 | P 中位数 | P 范围 | P 总量 |
|---|---:|---:|---:|---:|
| 每题首轮 | 60 | 3924 | 2156–4823 | 222825 |
| 新开放函数说明的用户轮 | 18 | 1398.5 | 802–2764 | 27207 |
| 其他非工具返回请求 | 204 | 358.5 | 75–1230 | 78974 |
| 工具返回后的请求 | 513 | 38 | 18–240 | 22626 |

这些是 token 统计，不是延迟占比。工具返回追加量仅占全部追加 token 的 6.4%，不能由此推断端到端收益比例。

- **首轮工具目录/说明**：确有几千 token，最接近稳定前缀缓存的规模。它对应跨任务启动成本，不属于每次 Tool Gap 的新增工作。已有长 H 的持久驻留不能重复计算成新收益。
- **新增函数说明**：现适配器把新增定义放进 tools schema，同时在当前用户消息正文中给出新增说明，可能导致说明重复及原历史重新计算。例如 `multi_turn_miss_func_194` 的 `t05-s00`，H=2750、P=2764，新增 `contact_customer_support` 名称在 prompt 出现两次。重组新增说明的位置比燃油字段更值得分析，但要区分新增文档自身长度与打断前缀后的历史重算。
- **当前工具返回**：大部分只有几十 token，现有 216 个通过任务后工具边界均保留完整 H_issue；尚未发现“早期变动使几千 token 静态长尾每步失效”的现象。

新增函数属于 miss_func 的有意限制，不能在公开前把其描述作为 all-inclusive 工具目录提供给模型。任何位置重组都必须保持公布时点、可调用工具范围及官方任务语义，重新验证质量。

ToolSandbox 首轮 CPU 73 题的 217 对相邻请求，工具描述发生变化的次数为 0；有 39 种跨任务工具名集合。因此跨任务工具目录复用值得单列评估，但没有证据表明它在这批 Tool Gap 内反复失效。工具名集合相同也还需核对描述全文、顺序和完整前缀。

## 对主线的选择

保留 route+always prepare 作为当前实测，不为了几个字段 token 引入新的主要机制或宣称收益。把短字段前缀放在可选消融项。

若继续扩展 Tool Gap，应首先寻找真实工作负载中在 gap 开始前已经确定的长片段：例如下一阶段固定指令与示例、确实重复的检索模板、可证明与本次动态值无关的长内容。只有观察到足够大的片段和实际可用 G，才值得设计预算化前缀候选/准备策略。这些长片段尚未在当前 513 个后工具边界中得到验证，不用人工增加样例来制造优化空间。

单个候选的有效性应通过真实成对计时判断：在准备已完成的条件下，比较原始 P 的 prefill 与准备 q token 后剩余输入的 prefill，再计入返回路径上的验证、状态提交和选路成本；另检查准备时间是否被真实 G 覆盖。recurrent/conv 状态的正确提交与失败回退是必要条件。

复现：

```sh
python scripts/analyze/promptweaver_fit.py \
  --bfcl results/20261108-bfcl-text-pilot \
  --toolsandbox results/20261107-toolsandbox-full/cpu \
  --output results/20261109-tool-return-structure
```

输出为 `promptweaver-fit.json` 和 `prompt-regions.json`。未修改手机上正在运行的 prompt、模型、路由与计时。

## 校正：逻辑公共前缀不等于运行时缓存命中

上一节的 P 规模不能证明这些请求都没有用到前缀。重新逐 token 比较 735 对相邻请求，得到：

- 513 个后工具边界中，0 个在上次 prompt 内分叉。512 个完整保留上次 prompt+generated token 序列，另 1 个在生成尾部有差异。长说明和旧 prompt 已在逻辑 H 内，不是新机会。
- 18 个新增函数说明请求全部在旧 prompt 内分叉；新增说明插在原 `<tools>` 尾部，故已有工具描述仍在 H，插入点之后的模板和历史不再能直接沿用旧状态。例如 `multi_turn_miss_func_194/t05-s00`：上次输入 4956 token、输出 245 token，本次输入 5514 token；H=2750、P=2764。分叉后与旧序列仍有 2447 个相等 token，最长连续相等块 2202 token，说明主要不是新增文档自身。上下文改变后，即使长尾 token 相同也不能直接复制其旧状态。
- 204 个其他非工具返回请求全部在旧 prompt 内分叉。观察到跨用户轮重新渲染历史 assistant 消息时，已有 `<think>...</think>` 段被移除。例如 `multi_turn_base_17/t01-s00` 的 H=3818、P=175，上一轮 prompt 为 3894 token、生成 72 token。此类首先是历史模板稳定性问题，不应直接命名为 PromptWeaver 式新机制；具体原因仍要逐类检查。
- 首轮按单任务比较定义 H=0，不代表服务没有跨任务前缀缓存。已保存的主机 vLLM usage 的 `prompt_tokens_details` 为 null，无法从这些字段证明实际缓存命中或未命中。

当前手机冻结 replay 主动构建或恢复完整 H，并从 H 开始测量 P；它不测首轮缓存，也不测上述跨用户轮前缀失效。手机 live service 的锚点恢复还有额外限制：只有整个保存锚点都是新 prompt 的前缀时才复用，不能任意截取 recurrent 状态。因此逻辑最长公共前缀、live service 的实际锚点和 vLLM 的物理缓存命中必须分别报告。

据此，正常后工具请求不能再申领静态工具说明缓存收益；新增函数说明只有分叉后的部分可能受益；普通跨用户轮先检查并修正模板一致性。`prefix-verification.json` 保留本次逐 token 核对记录，`promptweaver-fit.py` 也加入了可复现的旧 prompt 内分叉计数。

原始测量仅保留在本地 results/ 及 wins outputs 对应具名目录，不随 Git 推送。
