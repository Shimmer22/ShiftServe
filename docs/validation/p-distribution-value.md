# P 分布投机价值：探索与设备验证

结论：旧 cost-aware 是存在性判定，在已有审计中准备 54/54 次，42 次最终走 CPU。最小分布机制能减少投机准备，但本轮没有获得响应加速，不能宣布比 always 更优。

## 机制与独立变量

过去 8 个已返回 P 的经验直方图，预测下一次分布；无历史不投机。仅覆盖精确 P，不做均值 P 插值。Tool 发起前计算 `E[返回后按需准备的响应成本 − 提前准备的响应成本] − λA`，大于零才准备。A 为独立校准准备时间最大值；本次 86.52ms。λ=0.5，表示投机预算惩罚，不是测得的能耗系数或总资源目标。Gap 估计固定200ms，仅为受控条件，未宣称预测自然Gap。

P24 HC不划算，P32 HC划算。在长Gap下，相对按需准备，P32的投机收益上限是 A，故本次触发约为 Pr(P32)>0.5。λ=0 则任意正概率收益可能触发，仍易退化成 always；λ=1 在该基线下通常不触发。这些取舍必须显式报告，不能靠改名字规避。

设备：小米14Pro，Termux SSH；显式 hybrid，CPU权威状态/CPU decode，HTP候选，无KV整理、预搬移、repack；真实HTTP文本，未执行生成动作。固定H4096，P24连续12次、P32连续12次、交替12次。每事件always与分布策略随机相邻执行，共36配对、72次正式测量，另12次独立校准。预测器在一对完成后更新一次，不使用当前P。未准备时实际执行Post-tool选路，仍可按需准备HC。

## 实测

| 指标 | Always | 分布策略/变化 |
|---|---:|---:|
| 投机准备率 | 100% | 38.9%（14/36） |
| 准备后仍走CPU | 18次 | 4次 |
| 完整响应均值（发起HTTP至发布） | 2214.49ms | 2272.69ms |
| 配对完整响应差（分布−always） | — | +58.19ms（+2.63%） |
| 返回后响应差 | — | +32.93ms |
| 实际Gap差 | — | +25.26ms |
| 每事件总准备时间节省 | — | 31.81ms |

| 到达阶段 | 投机率 | 完整响应差ms | 返回后响应差ms | 准备节省ms |
|---|---:|---:|---:|---:|
| P24为主 | 0% | +72.23 | +24.11 | +83.19 |
| P32为主 | 58.3% | +65.81 | +58.28 | −1.70 |
| 交替 | 58.3% | +36.54 | +16.40 | +13.94 |

8次P32被跳过投机后仍正确走按需HC。分布切换时窗口适应慢，交替期也存在准备P24而错过P32的情况。它验证了概率门控和无未来信息的执行闭环，但没有证明该窗口预测器适合真实工具。完整响应差的配对bootstrap均值区间为[20.74,109.08]ms，仅描述本会话，不能当跨会话置信区间。

如果另用“完整响应+0.5×实际总准备时间”评价，本次分布策略也约差42.29ms；不支持已经改善整体成本的说法。实际Gap波动、校准成本误差与状态/缓存影响均保留；不能把减去Gap后的差当作精确因果效应。

- `device-summary.json`：全部配对、预测分布、按阶段汇总。
- 原始正式设备目录：`results/20261106-131813-106179-http-oracle-grid/`。
- 诊断试跑：`results/20261106-131344-709013-http-oracle-grid/`，发现“不准备只能CPU”与价值基线不一致后主动中止，保留25条记录，不进入正式收益统计。
- 正式收尾原Oracle分析器因不符合完整矩阵拒绝；已用专用配对分析器完整验收，并修正实验入口的分析分派，不重跑/筛选设备样本。

后续最有价值的方向是采集按工具类型分组的自然P/Gap轨迹，以时间顺序训练/测试直方图，先衡量预测校准与切换误判，再比较λ和窗口。纯响应延迟目标保留always作为强基线；资源目标需明确准备预算或实测能耗，不能只凭准备率宣布收益。
